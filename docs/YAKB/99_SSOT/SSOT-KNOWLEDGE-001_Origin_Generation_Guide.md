# SSOT-KNOWLEDGE-001: Origin Seed 생성 가이드

---

**최상위 Authority:** `docs/YAKB/00_ARCHITECTURE/Architecture_Constitution.md` (SSA — Foundation. 본 문서와 Constitution이 충돌하면 Constitution이 우선한다)
**목적:** Legacy Website의 모든 장소/관광지/코스를 동일한 품질의 Origin Seed로 생성하기 위한 표준 절차를 정의한다.
**상태:** 표준 확정 (ORIGIN-001 오동도, ORIGIN-002 향일암 파일럿 2건의 실제 작업 경험을 근거로 작성)

**근거 자료:** `ORIGIN-001_Odongdo.md`, `ORIGIN-002_Hyangiram.md`, `Inventory.md`, `SQL_Analysis.md`, `Legacy_to_Seed_Plan.md`
**적용 대상:** 이후 생성되는 모든 `ORIGIN-xxx.md` (거문도백도 이하 8개 대기 후보 포함)

## 1. 목적

Origin Seed는 Legacy 데이터를 AI가 재사용 가능한 Journey Knowledge로 변환하는 **최초 단계**이다.

Origin Seed는 장소·관광지 그 자체(오동도, 향일암 등)를 다루는 Seed 유형으로, Route/FAQ/Restaurant/Hotel 등 다른 모든 Seed 유형이 참조하는 기초 지식층이다. Origin Seed의 품질이 낮으면 그 위에 만들어지는 모든 결과물(Journey, DreamTown, 유튜브, 상담 스크립트 등)의 품질도 낮아진다. 따라서 Origin Seed는 **작성자에 따라 품질이 들쭉날쭉해서는 안 되며**, 이 문서가 정의하는 절차를 예외 없이 따른다.

## 2. 입력 Source 우선순위

Legacy 사이트는 동일한 "지역명소" 지식이 여러 계층(정적 페이지, 게시판, 이미지, 코드)에 흩어져 있다. 아래 우선순위대로 확인하며, **순위가 높은 Source가 항상 더 신뢰할 수 있다는 뜻이 아니라, 항목별로 얻을 수 있는 정보의 종류가 다르다는 뜻**이다 — 4개 우선순위를 전부 확인해야 완전한 Origin Seed가 된다.

### Priority 1 — 정적 HTML (`include/sub/*.html`)

- 확정된 라우팅 규칙: 메뉴 "지역명소"(MM=05)는 `/aksa/?MM=05&SM={코드}` URL로 서비스되며, 실제 콘텐츠는 `include/sub/sub{MM}_{SM}.html`에 있다. (예: 오동도 = `sub05_01_01.html`, 향일암 = `sub05_01_03.html`)
- 이 계층에서만 얻을 수 있는 정보: **전설/설화, 창건·개칭 역사, 감성적 서술, GPS 좌표(Daum 지도 임베드가 있는 경우), 이미지 파일명**
- `include/left_menu_05.php`에서 전체 SM 코드 목록과 목적지명을 먼저 확인할 것 (Legacy_to_Seed_Plan.md 6-1절에 9개 후보 목록이 이미 정리되어 있음)
- **주의**: 모든 정적 페이지가 오동도·향일암과 동일한 구조(전설 2건 + 역사 + 사진 3세트 + 위치)를 가진다고 가정하지 말 것. 페이지마다 실제로 열어서 구조를 확인한다.

### Priority 2 — SQL 게시글 (`g5_write_*`)

- 대상 게시판: `infomation`, `travel_tm`, `knowhow`, `knowhow1`, `qa`, `fa` (Priority 1 게시판, SQL_Analysis.md 참조)
- `local`(舊 "지역명소" 게시판)은 **빈 고아 게시판이므로 검색 대상에서 제외**한다 — 대신 Priority 1 정적 페이지가 이 역할을 한다.
- 이 계층에서만 얻을 수 있는 정보: **운영 정보(입장료, 운영시간, 연락처, 주차), 교통편(버스 노선), 코스/일정 내 위치, 조회수(Seed Score 산정 근거)**
- 키워드 검색은 `wr_subject`, `wr_content`, `ca_name` 세 필드 모두 대상으로 한다.
- **`knowhow1`은 `knowhow`의 명시적 복사본**("[복사본] 여순광길잡이", g5_board 확정)이지만, **완전히 동일하다고 가정하지 말 것** — ORIGIN-002 작업에서 `knowhow1`에만 존재하고 `knowhow`에는 없는 게시글(wr_id=81, 향일암 버스시간표)이 발견되었다. 두 게시판을 항상 함께 검색한다.

### Priority 3 — 이미지 자산 (JPG/PNG, 파일명, ALT 정보)

- 정적 페이지 내 `<img>` 태그에서 파일 경로(`_img/sub/*`)를 추출하고, 파일 시스템에 실제로 존재하는지 확인한다.
- 파일명 패턴에서 목적지를 추정할 수 있다 (예: `odong*` = 오동도, `hyang*` = 향일암).
- **ALT 텍스트는 원문 그대로 신뢰하지 말 것.** ORIGIN-001·002 두 사례 모두에서 ALT 텍스트가 실제 이미지 내용과 무관한("거북선축제", "이순신광장" 등) 값으로 통일되어 있음이 확인됨 — 사이트 제작 시 다른 페이지의 ALT 템플릿을 복사한 것으로 추정. 상세 규칙은 7절 참조.

### Priority 4 — PHP 코드 (메뉴 구조, URL, 링크)

- `g5_menu` DB 테이블은 **양쪽 사이트 모두 비어있어(0건) 신뢰할 수 없다.** 메뉴-URL 매핑은 반드시 코드에서 확인한다.
- 확인 대상 파일: `board.navi.php`(게시판별 `$MM`/`$middle` 라우팅), `include/left_menu_{MM}.php`(서브메뉴 실제 항목·라벨)
- 이 계층에서 얻는 정보: 이 목적지가 **실제로 활성 메뉴에 연결되어 있는지**(고아 게시판/페이지 판별), 정확한 한글 메뉴 라벨, 관련 목적지 간의 메뉴 구조상 인접 관계

## 3. 생성 절차

```
1. Source 수집        — 위 4개 Priority를 순서대로 확인, 전부 수집 전에는 다음 단계로 넘어가지 않는다
      ↓
2. 중복 제거          — knowhow/knowhow1 등 미러링 게시판 통합 (6절 규칙 적용)
      ↓
3. Source Trace 기록  — 수집 단계에서부터 표로 기록해 둘 것 (사후 재구성 금지, 5절 규칙)
      ↓
4. Origin Seed 생성   — 4절 표준 구조에 맞춰 작성
      ↓
5. Seed Score 계산    — 8절 공식 적용
      ↓
6. 검증               — 9절 완료 기준 체크리스트 전항목 통과
```

**절차 위반 사례 방지**: ORIGIN-001은 최초 SQL 게시글만으로 생성되었다가, 이후 정적 페이지(Priority 1)를 놓친 것이 뒤늦게 발견되어 재작업했다. 이 문서 확정 이후에는 **Priority 1(정적 HTML) 확인을 반드시 Source 수집의 첫 단계로 삼아** 이런 재작업이 재발하지 않도록 한다.

## 4. Origin Seed 표준 구조

모든 `ORIGIN-xxx.md`는 아래 9개 섹션을 이 순서대로 포함한다. 목적지 특성에 따라 각 섹션 내부에 하위 소제목(예: "4. 기본 정보" 안에 "연락처", "유람선/코스" 등)을 추가하는 것은 허용되나, **9개 섹션 자체를 생략하거나 순서를 바꾸지 않는다.**

| # | 섹션 | 내용 |
|---|------|------|
| 1 | 핵심 정보 | 500자 내외 요약 — 이 Seed 하나만 읽어도 목적지의 전체 그림이 그려져야 함 |
| 2 | 원본 스토리 | 정적 페이지(Priority 1)의 전설·설화·감성 서술 원문 인용 |
| 3 | 역사 | 창건/개칭/화재·재건 등 시간순 사실 (연도 명시 필수) |
| 4 | 기본 정보 | SQL 게시글(Priority 2) 기반 운영정보 — 주소, 연락처, 입장료, 운영시간, 교통편 |
| 5 | 이미지 자산 | 파일명·경로·ALT 텍스트·실존 확인 결과 (7절 규칙 적용) |
| 6 | Journey 해석 | 이 목적지가 여행 코스·타 목적지와 어떻게 연결되는지 (예: ORIGIN-001↔ORIGIN-002처럼 같은 게시글에 함께 등장하는 관계) |
| 7 | Source Trace | 5절 규칙에 따른 전체 출처 표 (필수, 생략 불가) |
| 8 | Output | 이 Seed에서 파생 가능한 결과물 체크리스트 (FAQ/Journey/DreamTown/유튜브/블로그/상담/예약/Voice/PPT 등, 최소 5개 이상) |
| 9 | 다음 단계 | 미해결 의문점, 후속 확인 필요 항목, 다음 Origin 후보 진행 상황 갱신 |

> 참고: "제외된 정보"(관련 없어 배제한 게시글과 사유)와 "Trust Level 근거"는 위 9개 섹션 중 각각 4절(기본 정보)과 7절(Source Trace) 인근에 하위 소제목으로 포함시킨다 — 별도 최상위 섹션으로 두지 않는다.

## 5. Source Trace 규칙

Source Trace는 Origin Seed에서 **생략이 허용되지 않는 유일한 섹션**이다. 아래 필드를 반드시 표 형식으로 기록한다.

| 필드 | 설명 | 비고 |
|------|------|------|
| Source Type | 정적 HTML / SQL 게시판 / 이미지 / PHP 코드 중 하나 | |
| 파일 | 정적 HTML·PHP 코드의 경우 상대 경로 | 예: `include/sub/sub05_01_03.html` |
| bo_table | SQL 게시글의 경우 게시판명 | 예: `knowhow`, `knowhow1`, `fa` |
| wr_id | SQL 게시글의 경우 게시글 ID | 중복 출처는 `{번호}-dup` 형식으로 병기 |
| 작성일 | SQL은 `wr_datetime`, 정적 파일은 확인 불가 시 "—" 표기 | 임의로 추정하지 않는다 |
| 이미지 경로 | 이미지 Source인 경우 `_img/sub/*` 등 실제 경로 | 파일 실존 확인 결과도 함께 기록 |
| URL | 해당 콘텐츠의 원본 서비스 URL (알 수 있는 경우) | 예: `/aksa/?MM=05&SM=01_03` |

각 행에는 위 필드 외에 조회수·작성자·역할(주 출처/보조 출처/제외 사유) 컬럼을 추가해도 된다 — ORIGIN-001, ORIGIN-002의 Source Trace 표를 기본 서식으로 삼는다.

## 6. 중복 처리 규칙

```
동일 게시글 발견
      ↓
g5_board.bo_subject로 공식 관계 확인   ← "복사본"이라는 문구가 있는지 직접 확인 (추정 금지)
      ↓
대표 Source 지정                      ← 조회수가 더 높은 쪽 또는 원본 게시판(예: knowhow) 우선
      ↓
중복 Source 병기                      ← Source Trace에 "{번호}-dup"로 남기고 삭제하지 않음
```

- "동일 게시글"의 판단 기준: `wr_subject`, `wr_datetime`, `wr_content` 핵심 내용이 실질적으로 같을 것. 제목만 비슷하고 내용이 다르면 중복 처리하지 않는다.
- **예외 처리**: 중복 게시판 쌍(예: knowhow/knowhow1)이라도 한쪽에만 존재하는 게시글이 있을 수 있다(6-1절 실사례: knowhow1-81). 이런 게시글은 중복이 아니라 **독립 출처**로 표기한다.
- 대표 Source를 정할 때 조회수가 높은 쪽을 우선하되, 게시판 자체가 "복사본"으로 명명된 경우(`knowhow1`)에는 원본 게시판(`knowhow`)을 대표로 지정하는 것을 기본값으로 한다.

## 7. 이미지 규칙

세 가지를 반드시 확인한다.

1. **실제 파일 존재 확인** — 정적 페이지의 `<img src="...">` 경로를 파일 시스템에서 직접 확인한다(예: `ls _img/sub/{파일명}`). 존재하지 않는 이미지 참조는 Source Trace에 "누락"으로 명시한다.
2. **ALT 불일치 확인** — ORIGIN-001(오동도)·ORIGIN-002(향일암) 두 사례 모두에서 ALT 텍스트가 실제 이미지 내용과 무관하게 "거북선축제/이순신광장" 테마로 통일되어 있음이 확인되었다. **모든 신규 Origin Seed에서 이 패턴이 반복되는지 우선 확인**하고, Seed 문서에 원문 ALT 텍스트를 그대로 표로 남기되 "⚠ ALT 텍스트 불일치" 주석을 병기한다. Output 제작 시에는 이미지를 육안으로 확인한 뒤 사용하도록 안내 문구를 넣는다.
3. **누락 여부 확인** — 정적 페이지에 이미지가 없거나(예: 오동도의 "위치" 섹션처럼 이미지 대신 텍스트만 있는 경우), 반대로 지도 API(Daum 지도 등)로 대체된 경우(향일암 사례)를 구분해서 기록한다. 후자는 GPS 좌표를 직접 추출해 Seed에 포함시킨다(2-5절 참조, ORIGIN-002 사례).

## 8. Seed Score

### 8-1. 기본 공식 (Legacy_to_Seed_Plan.md 원안, 그대로 유지)

```
Seed Score = (조회수 / 100) + (추천수 × 5) + (이미지수 × 2)

10점 이상 → Priority 1 즉시 변환
7~9점    → Priority 2
5~6점    → Priority 3
4점 이하  → Archive 보존, 변환 보류
```

### 8-2. Source 다양성 가점 (v1.0 신규 규칙)

Origin Seed는 태생적으로 여러 Source(정적 HTML + SQL + 이미지 + PHP 코드)를 통합하는 유형이므로, 확보한 **독립 Source 유형의 개수**에 따라 가점을 추가한다.

```
Source 다양성 가점 = (확보한 독립 Source Type 개수 − 1) × 3
  (Source Type: 정적 HTML / SQL 게시판 / 이미지 / PHP 코드 — 최대 4종)

최종 Seed Score = 기본 공식 값 + Source 다양성 가점
```

**예시 (ORIGIN-002 향일암 기준 재계산)**: 정적 HTML + SQL 게시판 + 이미지 3종 확보 → 다양성 가점 = (3−1)×3 = 6점. 기본 공식값 29.58점 + 6점 = **35.58점**.

> **정정 이력 안내**: 이 가점 규칙은 ORIGIN-001·ORIGIN-002 작성 **이후**에 확정되었으므로, 두 문서에 기록된 Seed Score(각 31.6점, 29.6점)는 8-1절 기본 공식만 반영한 값이다. 두 문서를 소급 수정할지는 별도 작업(TASK)으로 판단하며, 이 가이드는 **ORIGIN-003부터 적용**한다.

## 9. 완료 기준

Origin Seed를 "완료" 상태로 표시하려면 아래 항목을 전부 체크할 수 있어야 한다.

- [ ] Source Trace 작성 (5절 필드 전부 포함)
- [ ] 정적 HTML 확인 (Priority 1 — 존재하지 않으면 "정적 페이지 없음"을 명시적으로 기록)
- [ ] SQL 확인 (Priority 2 — `knowhow`/`knowhow1` 양쪽 모두 검색했는지 포함)
- [ ] 이미지 확인 (Priority 3 — 실존 여부 + ALT 불일치 여부, 7절)
- [ ] 중복 제거 (6절 규칙에 따라 대표/중복 Source 구분 완료)
- [ ] Journey 해석 (타 목적지·코스와의 관계 최소 1개 이상 서술)
- [ ] Seed Score (8절 공식 적용, 계산 과정 명시)

이 중 하나라도 미완료면 문서 상단 **상태** 필드에 "초안" 또는 "부분 완료"로 표기하고 완료로 표기하지 않는다.
