# RFC-004: 나눔 이중 정의 검토

---

**목적:** "나눔"이 리액션 시스템(기적나눔/감사나눔/지혜나눔)과 삶의 철학(소망이가 되는 과정)이라는 두 의미로 쓰이는 현상을 분석하고, 어디서 정의해야 하는지 권고한다.
**상태:** **검토 완료 — Decision 아님(Review Only).** 이 문서는 분석과 권고안만 담으며, 어떤 기존 문서도 수정하지 않았다.
**작성일:** 2026-07-04
**대상 문서(수정 없이 참조만 함):** `SSOT-LANG-001` 8절, `SSOT-JOURNEY-001` 7절, `Architecture_Constitution.md` 제3장
**금지 사항 준수:** Experience Constitution을 작성하지 않았다. `SSOT-LANG-001`을 수정하지 않았다.

---

## 1. 현황

"나눔"은 현재 두 가지 뜻으로 쓰인다.

| # | 의미 | 출처 |
|---|------|------|
| ① | **리액션 시스템** — 기적나눔·감사나눔·지혜나눔(Like/Comment/Thanks 대체), `DtNanum` 모델로 실제 코드 구현됨 | `SSOT-LANG-001` 8절, `Project_Phoenix_Language_Audit.md` |
| ② | **삶의 철학** — Journey의 완성. "소원이는 소망이가 되어 다른 예비 소원이의 Journey를 돕는다" | `SSOT-JOURNEY-001` 7절, `Architecture_Constitution.md` 제3장(성장 모델: 소원→회복→성장→나눔→새로운 소원) |

---

## 2. 검토 내용

### 2-1. 두 의미가 충돌하는가

**직접 충돌은 아니다.** 문맥으로 대부분 구분된다 — ①은 버튼을 누르는 구체적 행위, ②는 삶의 한 국면을 가리키는 추상적 원칙이라 같은 문장 안에서 섞일 일이 거의 없다.

다만 **"측정 대체" 위험이 있다.** ②(철학적 나눔)는 본래 측정하기 어려운 추상 개념인데, 제품에는 ①(리액션 클릭 수)이라는 손쉬운 측정 가능한 지표가 이미 존재한다. 앞으로 "이 사용자가 나눔을 실천했는가"를 판단해야 할 때, **①의 클릭 수를 ②의 달성 여부로 슬쩍 대체해버릴 위험**이 실질적으로 있다 — 이것이 이번 검토에서 발견한 진짜 리스크이며, 단순 "명칭 충돌"보다 더 중요하게 다뤄야 할 지점이다.

### 2-2. 공존 가능한가

**가능하다. 오히려 이미 이 프로젝트가 반복해서 써온 패턴에 가장 가깝다.** 단, 재방문/재회 사례(`RFC-LANG-001`)와는 다른 방식의 공존이라는 점을 구분해야 한다.

| 사례 | 공존 방식 |
|------|-----------|
| 재방문 / 재회(`RFC-LANG-001`) | **서로 다른 두 단어**를 서로 다른 두 청중(운영 vs 경험)에 배정 |
| 나눔 / 공명(`SSOT-LANG-001` 8절) | **서로 다른 두 단어**를 서로 다른 두 리액션 체계에 배정 |
| **나눔①(리액션) / 나눔②(철학) — 본 RFC** | **같은 한 단어**가 "포괄 개념(②)"과 "그 개념의 구체적 실천 방식 중 하나(①)"라는 **상위-하위 관계**로 이미 자연스럽게 성립함 |

즉 이번 사례는 "충돌하는 두 정의 중 하나를 고르거나 새 단어로 나눠야 하는 문제"가 아니라, **"나눔(철학)이 나눔(리액션)을 포함한다"는 이미 성립해 있는 위계 관계를 명문화하기만 하면 되는 문제**다. 새 단어를 만들 필요가 없다.

### 2-3. 정의 위치 권고 — Language Constitution vs Experience Constitution

| Constitution | 이미 다루고 있는 것 | 이번 건에 대한 역할 |
|---------------|----------------------|----------------------|
| **Language Constitution**(`SSOT-LANG-001`) | "나눔"이라는 **이름**을 리액션 3종에 붙이는 결정(8절) — 이미 완료됨 | 의미②(철학)를 여기서 새로 정의할 필요 없음 — Language Constitution은 이름을 정하는 문서이지 원칙을 선언하는 문서가 아니다(2절 Language Architecture 원칙) |
| **Architecture Constitution** | 의미②(나눔=성장 모델의 한 단계)를 **이미** 제3장에서 선언함 | 원 소유자 — 재정의 불필요, 이미 있음 |
| **Journey Constitution**(`SSOT-JOURNEY-001`) | 의미②를 Journey 완성 원칙으로 **이미** 7절에서 재확인함 | 원 소유자와 일치 — 재정의 불필요 |
| **Experience Constitution**(미작성) | 아직 없음 | **"나눔(철학)이 나눔(리액션)으로 어떻게 구현되는가"라는 상위-하위 연결 관계를 명문화하기 가장 적합한 자리** — Experience Constitution의 존재 이유가 바로 "원칙이 실제 경험/UX로 어떻게 이어지는가"를 다루는 것이기 때문 |

**권고**: 의미①과 ②를 각각 다시 정의할 필요는 없다(이미 각자의 자리에 정확히 정의돼 있음). 필요한 것은 둘의 **관계**(포괄 개념 vs 구체적 실천)를 명문화하는 것 뿐이며, 이 "관계 설명"은 Language Constitution도 Architecture/Journey Constitution도 아닌 **Experience Constitution의 몫으로 남겨두는 것을 권고한다.** Experience Constitution이 아직 없으므로, 이 RFC는 그 내용을 대신 작성하지 않고 향후 과제로만 남긴다.

### 2-4. 임시 완화책 (Experience Constitution 작성 전까지, 실행은 보류)

Experience Constitution이 만들어지기 전까지, 아래와 같은 한 줄 각주를 `SSOT-LANG-001` 8절에 추가하면 2-1의 "측정 대체 위험"을 낮출 수 있다는 점만 권고안으로 남긴다(**이번 RFC에서 실행하지 않음**):

> (권고 문구 예시) "나눔(기적나눔/감사나눔/지혜나눔)은 나눔 철학(Architecture Constitution 제3장, Journey Constitution 7절)의 구체적 실천 형태 중 하나일 뿐, 그 클릭 수가 곧 나눔 철학의 달성 여부를 의미하지는 않는다."

## 3. 완료 보고 요약

| 확인 항목 | 결과 |
|-----------|------|
| 충돌 여부 | 직접 충돌 아님. 다만 "리액션 클릭 수를 철학적 나눔 달성의 증거로 대체"하는 **측정 대체 위험**이 실질적으로 존재 |
| 공존 가능 여부 | **가능** — 재방문/재회처럼 "두 단어"로 나눌 필요 없이, "포괄 개념(철학) - 구체적 실천(리액션)"의 **상하위 관계**로 이미 자연스럽게 성립 |
| 정의 위치 권고 | 의미①·② 모두 이미 올바른 자리(Language / Architecture·Journey)에 정의되어 있어 재정의 불필요. 둘의 **관계**를 명문화하는 것만 남았으며, 이는 **Experience Constitution의 몫**으로 권고 |
| 실행 여부 | **미실행** — `SSOT-LANG-001`, `Architecture_Constitution.md`, `SSOT-JOURNEY-001` 어느 것도 수정하지 않았으며, Experience Constitution도 작성하지 않았다 |
